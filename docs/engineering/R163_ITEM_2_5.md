# r163 item 2.5 — app-engine Phase 5: persistence wiring (implemented)

Authority: `docs/engineering/APP_ENGINE_REPAIR_PLAN.md` §4 Phase 5 ("wire it, do not design
it"), defects D10/D10a. On top of Phase 2 (`c9490403`). This file records what the code does.

## 1. What was missing

The save CONTRACT was already proven (envelope, CRC, temp-then-rename, corrupt/absent/over-cap
→ fresh start, `kVolatileOnly`). What was missing was every HOST side of it:

* nothing ran a save at exit, so a blob sitting in RAM died with the activity (D10);
* there was no entry point a program could declare for "persist now", so state changed outside
  a tap (a timer, a tick counter) had no way to be written at all (S7);
* `kVolatileOnly` said nothing to the PERSON holding the device -- only to the log (D10a).

## 2. `on_save` — the entry point (VM side)

| where | what |
|---|---|
| `src/engines/core/Program.h:66-89` | `kNoSaveEntry` + the amendment note (optional; arity 0; may not paint; idempotent) |
| `src/engines/core/Program.h:111` | `ProgramHeader::saveEntry`, defaulted to the sentinel |
| `src/engines/core/Program.cpp:239-249` | verify: out of range, aliasing any other root, **declared without `kFlagRequiresSave`** |
| `src/engines/core/Program.cpp:327-329` | verify: must be an instruction boundary |
| `src/engines/core/Program.cpp:434-437` | the depth pass seeds it as a FOURTH root at depth 0 (no operands) |
| `src/engines/core/Vm.h:227-246` | `runSave()` / `hasSaveHandler()` + the event contract |
| `src/engines/core/Vm.cpp:213-235` | `Vm::runSave` — `E_V_SAVEKEYS` and **zero steps** when there is no handler; never redirected to the action entry |
| `src/engines/core/Vm.h:121` | `EventKind::kSave` |
| `src/engines/host/CpbLoad.cpp:60-64` | every decoded `.cpb` answers `kNoSaveEntry` |

**The one part that could not be landed end to end.** `saveEntry` is not a `.cpb` header word:
the header is 52 bytes and the next byte is the first code word, so a save entry needs a
56-byte header and a bytecode version bump — i.e. `tools/vm/cpvm_format.py` and
`build_apps.py`, which this batch may not touch. `decodeCpb` therefore answers `kNoSaveEntry`
for every file today, every current app verifies byte-identically, and the host half (verify,
dispatch, flush) is complete: the day the toolchain emits offset 52, no device code changes.
This is recorded in `Program.h`'s WIRE NOTE on the constant rather than left implicit, so the
next author sees a blocked wire rather than an empty field.

Consequence for the operator: **no app declares `on_save` yet**, so the flush that runs on the
glass today is the pending-blob retry (§4) — which is the D10 case and needs no app support.

## 3. The exit flush (host side)

`src/activities/EngineHostActivity.cpp`:

| line | what |
|---|---|
| `onExit()` :148 | `flushSave()` first (VM and ports still bound), then the log line, then `paintSaveNotice()`, then the orientation restore |
| `flushSave()` :191 | 1. run `on_save` if declared — one action-shaped run, **no drive**, a fault is logged and swallowed; 2. `flushPending()` the pending blob; 3. set `saveVolatile_` from the result |
| `paintSaveNotice()` :234 | one 44 px band at the bottom of the app's own canvas, one GL16 drive, only when the save really did not land |

Ordering is the point: the flush runs while `vm_`, `hostPorts_`, `canvas_` and `saveIo_` are
still alive, and the notice is drawn in the app's own orientation before that is restored.

A fault inside `on_save` cannot block the exit — the user pressed Back, and a wedged exit is a
worse outcome than a lost save. That is `flushSave()`'s `r.error != E_OK` branch: one `LOG_WRN`
with the code, pc and step count, then continue.

## 4. The pending-blob retry (`SaveIo`)

| where | what |
|---|---|
| `src/engines/host/SaveIo.h:207-209` | `hasPending()`, `pendingBytes()`, `flushPending()` |
| `src/engines/host/SaveIo.cpp:298` | `flushPending()` — calls the **ordinary** `store()`, so the same temp-then-rename, size-verify and vouch gate apply; a success logs `exit flush: N byte save ... reached the card` |

`hasPending()` is exactly "the last store degraded to RAM" (`store()` clears the session on
success), so a session that saved normally flushes nothing — no second write, no extra wear.

## 5. The loud half

`paintSaveNotice()` replaces silence, not the log: both fire. The band says
`Progress was not saved -- the card is not writable.` in paper-on-ink at the bottom of the
app's own frame, and IS driven (one `kGl16`, rect = the band) so it is on the glass when the
activity leaves. The next screen repaints over it; the `[ENGINE]` warning survives the session.
It is painted only when `saveVolatile_` is set, and `noticePainted_` makes a second exit
impossible to drive twice.

## 6. Host proofs

* `test/cpvm_save/CpvmFlushTest.cpp` — **5 tests**: nothing pending after a good store (and the
  flush writes nothing twice); an unvouched save is pending and **lands when the card returns**
  (the D10 case, checked by reading the bytes back and by a fresh `load()`); a failed flush
  keeps the blob for a second attempt; an unattached store flushes nothing; a 1088-byte
  payload round-trips at a 2048 cap.
* `test/cpvm_core/CpvmSaveEntryTest.cpp` — **9 tests**: the sentinel default; absent is legal
  and runs **zero** steps; a declared handler runs as `kSave` with its own steps and stack; out
  of range; aliasing the action / tap / tick root (three cases); a non-boundary word; a
  handler without the save capability; a handler that pops an operand (zero arity); and a
  value-initialised `Program` declares no handler.
* `CpvmCoreTest` 894/894 and `CpvmSaveTest` 74/74 green after the change.

**Not provable on the host:** that the card receives the bytes at exit (the flush test proves
the store path, not the mount), and that the notice is legible on glass.

## 7. What still needs a decision

The `.cpb` header word. Adding it is a format change (52 → 56 bytes, version 3 → 4) plus
`build_apps.py`, `cpvm_format.py` and every `app.json`'s `"entry"` gaining `"save": "on_save"`.
It is deliberately NOT done here: `tools/vm` is out of this batch's scope, and a version bump
without the tools would strand every app (the r163 Phase-2 precedent).
